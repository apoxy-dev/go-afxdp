# gVisor patches

Applied to a checkout of gVisor's `go` branch (`go get gvisor.dev/gvisor@go`
resolves it) and used through the `go.work` in the parent directory. The
committed example builds against upstream without them; the fork only adds
knobs and fixes.

Every file the fork changes belongs to exactly one patch, and each patch is
that file's whole difference from upstream, so `for p in patches/*.patch; do
patch -p1 < $p; done` from the checkout's root reproduces the fork with no
rejects (checked against the pinned upstream). The numbers are the order the
work happened in; six of them no longer have a file of their own — their
change was to a file a later patch also changed, and lives there now — and
their rows stay in the table as "(folded into …)" because the change and
its reason still matter.

| patch | what | why |
|---|---|---|
| `0001` (folded into `0015`) | floor on the RACK reorder window; do not zero it at 3 SACKed segments | netstack mistook a 10G LAN's ordinary reordering for loss: 0.83 → 3.21 Gbit/s one-way. `-tags gvisorfork` exposes `-reorder-window` (default 5 ms). |
| `0003` (folded into `0011`) | `PacketData.ChecksumAtOffset` adds the packet's data offset, as `PullUp` does | GRO's own checksum check read the wrong bytes once a link header was consumed, so it never merged anything. Upstream never hits it because fdbased marks checksums validated before GRO. Reported for upstream. |
| `0004` (folded into `0012`) | while the advertised window is zero, segments at or beyond RCV.NXT still have their ACK processed (their data is not consumed) | RFC 793's literal rule let a bidirectional bulk connection wedge: our window closed, the peer's retransmit at RCV.NXT was dropped with its ACK, our sender never advanced, our app never drained. Linux's `tcp_sequence` accepts that segment. Reported for upstream. |
| `0002-delayed-ack.patch` (`connect.go`, `endpoint_state.go`; its `snd.go` and `endpoint.go` parts are in `0014`) | `tcp.DelayedACKTimeout`: hold a pure ACK briefly when under 2 MSS is unacknowledged (RFC 5681 §4.2), so a reply carries it | upstream has no delayed ACK at all: every inbound batch is answered with a bare ACK, a second frame per request for request/response servers. `-tags gvisorfork` exposes `-delayed-ack` (default 500µs). |
| `0005-inline-tcp-processing.patch` | `tcp.InlineProcessing`: a segment for an established, uncontended endpoint is handled on the goroutine that delivered it (`handleEstablishedInline`, a TryLock and `handleSegmentsLocked`) instead of being queued for a processor goroutine; only when the flags carry no SYN, RST or FIN and the state stays ESTABLISHED, because the delivering goroutine holds the demuxer's read lock and a close would take it for writing. `tcp.TxHashFromRx` (same patch) copies the receive queue into the connection's transmit hash so replies leave on the socket the receive goroutine owns. | the handoff to a processor goroutine was one wakeup per request and most of the request/response gap to the kernel: 458k → 661k req/s at the time, the base of every later run-to-completion number. `-tags gvisorfork` exposes `-inline-tcp`, `-txhash-rx`. |
| `0006` (folded into `0014`) | `tcp.ProcessorCount`: how many TCP processor goroutines a stack starts (upstream: `GOMAXPROCS`) | with one stack per NIC queue, each needs one processor for the work the inline path cannot take, not `GOMAXPROCS` of them. `-tags gvisorfork` exposes `-tcp-processors` (default 1). |
| `0007-chunk-zero-on-reuse.patch` | `buffer.ZeroOnReuse`: skip clearing a pooled chunk when it is reused (default off in the fork) | every user of a fresh view writes it before anything reads it, so upstream's `clear` is a second pass over every received byte (1.25 GB/s of memset at 10G). `-tags gvisorfork` exposes `-chunk-clear` to put it back. |
| `0008` (folded into `0016`) | `MonotonicTime.Add`/`Sub` as integer arithmetic | upstream routes both through `time.Unix(...).Add(d).Sub(...)`, ~40 ns each, and TCP calls them several times per segment: with `time.Now` in `NowMonotonic` the clock was 9% of the request/response profile. The example also supplies its own `tcpip.Clock` that reads the runtime's `nanotime` once. |
| `0009-external-payload.patch` (`buffer/view.go`; the external-chunk half is in `0007`, the `endpoint.go` half in `0014`) | `buffer.NewViewFromExternal` / `NewViewFromExternalSized`: a view over caller-owned memory, never written by the stack, released by callback when the last reference goes — the sized form lets the stack count bytes the caller lays out with gaps (a cache with header room before each segment's payload), which the endpoint reads back through `View.External`; `tcp.Endpoint.WriteExternal(views)`: queue such views as one segment without the copy `Write` makes | transmit without copying payload: a frame that already sits in the UMEM goes from the application through TCP to the NIC untouched. One view per 45 frames keeps the stack's per-view work per packet; with one view per frame the bookkeeping cost more than the copy it saved. |
| `0010-segment-shares-packet.patch` | `newIncomingSegment` takes a reference to the delivered packet instead of cloning it (`tcp.ClonePacketForSegment` restores upstream) | after GRO a packet is ~35 views; cloning them (a pool get and a refcount per view, then the same to release the original) was 10% of the receive profile at 100G. The caller drops its reference on return and never touches the packet again. `-tags gvisorfork` exposes `-seg-clone`. |
| `0011-read-without-clone.patch` | `Buffer.SubSlices` walks views without cloning; `PacketData.ReadTo` uses it | the application's read cloned and released every view it handed out, ~8% plus the releases. With 0010, receive at 100G went from 9.0 to 6.6 cores at the wire and, at a 16-core budget, from 75 to 90 Gbit/s. |
| `0012-out-of-order-counter.patch` | `tcp.OutOfOrderSegments`: segments queued for reassembly, stack-wide | a diagnostic: whether a peer's reorder reports reflect delivery order here. It showed the 100G kernel client reordering its own stream (thousands per run) while the netstack client never did. |
| `0013` (folded into `0014`) | `tcp.PreciseRTT`: measure the round trip from the local clock even when the peer echoes a TCP timestamp | the timestamp option carries milliseconds; on a sub-millisecond link every sample from it reads as 1 ms and CUBIC grows the window as if the path were ten times longer. Linux prefers the clock sample; upstream's guard skips it whenever the option is present. `-tags gvisorfork` exposes `-precise-rtt`. |
| `0014-link-backpressure.patch` (`snd.go`, `endpoint.go`, `protocol.go`; carries `0002`'s, `0006`'s, `0009`'s and `0013`'s changes to them) | also `tcp.SeparateZeroWindowProbe`: a zero-window probe is sent on the retransmit timer and backed off the same way, but is not counted as a timeout and does not collapse the congestion window or reset the scoreboard — upstream treats a peer that has stopped reading exactly like loss, so every slow reader's pause restarted its connection from a minimal window (20000 slow connections: 840k timeouts and 2.7 cores, against none and 1.2 with it). And `tcp.LinkBackpressure`: a link's `WouldBlock` on write means "not sent, try again when told" — the attempt is undone (send time and count, SND.NXT not advanced, the delayed ACK it would have carried re-armed, no retransmit timer, no retransmit counted), the endpoint joins a per-stack line and stops sending; `tcp.ResumeBlocked(stack)` gives the line a turn each, `tcp.LinkTurn` segments (default 1), in order, first-timers first, stopping at the first refusal | upstream advances SND.NXT whether or not the link took the segment, so a link that has no room can only drop, and with 2000 connections behind one queue the drops became RTO storms. This is the sender half of TCP small queues; the link half is `xdplink`'s `TxBacklogHigh/Low` and `OnTxRoom`. `-tags gvisorfork` exposes `-link-backpressure`, `-link-turn`. |
| `0015-tail-loss-probe-floor.patch` (`rack.go`; carries `0001`) | `tcp.MinPTO` (default 10 ms): a floor under the tail loss probe timeout; `tcp.TLPSkipWindowLimited`: no probe is armed while the sender has data ready that only the peer's window holds back (that peer has the bytes and has not read them, so a probe can only retransmit what is not lost); `tcp.TLPProbes` and `tcp.RACKLossMarks` counters | upstream's probe timeout is twice the smoothed RTT with no floor; with `0013` that is a few hundred microseconds on a LAN, less than a peer's delayed ACK, so it probed and retransmitted almost every tail (3.8M probes in a 30 s run, every one DSACKed). Linux adds a fixed minimum and rounds up to a jiffy. `-tags gvisorfork` exposes `-min-pto`, `-tlp-skip-window-limited` and (for the probe's other half, in `0014`) `-zwp-separate`. Together they took the 50000-connection file row from 1.27M probes and 433k timeouts to 4.3k and 36. The trade in `TLPSkipWindowLimited`: a window-limited bulk sender whose tail is genuinely lost now recovers by RTO rather than by probe; on a lossy path that is worth turning off, at the cost of the spurious probes on slow readers. |
| `0016-churn-trims.patch` (`tcpip.go`, `timer.go`, `sack_scoreboard.go`; carries `0008`) | `tcpip.TrackDanglingEndpoints` (the fork turns it off): the sentry's save-time registry of closing endpoints, one global mutex twice per close, shared by every stack in the process. `timer.stop`, used when a sent segment carries the delayed ACK: the runtime timer is stopped rather than orphaned, so it does not wake a goroutine and take the endpoint's lock to find it has nothing to do — it did that once per request. A SACK scoreboard whose tree is built on the first SACK block, since most connections never carry one and the tree with its free list was the largest allocation an endpoint made. | on the connection-churn row (one 8 KiB–1 MiB object per connection, the netstack client driving): 60.2k → 61.7k connections/s on 4 cores for 3% less CPU; 106k → 110k on 8. What is left of the churn cost is the handshake (9% of the profile), the FIN (4%), endpoint construction and the collector. |
| (in `0005`) `tcp.BatchProcessing` | the work the inline path cannot do — a listener's SYN and the handshake, FIN and close — runs on the delivering goroutine after the batch (`tcp.DrainDeferred`) instead of waking a processor goroutine | the delivering goroutine holds the demuxer's read lock only during the batch, so afterwards it may take any lock; no wakeup, no contention with the receive goroutine's own sends. On the file workload at 4 cores: 22.3k → 25.0k connections/s, 61 → 69 Gbit/s; pure churn costs the same as the kernel (1.6 cores at 32k/s). `-tags gvisorfork` exposes `-batch-tcp`. |
| (in `0014`, originally `0013`) delayed-ACK timer disarmed when a sent segment carries the ACK | `sender.ackCarried` | a server that answers every request within microseconds otherwise pays a timer goroutine wakeup, an endpoint lock and a no-op check per request, a millisecond later (7% of the file-serving profile). |
